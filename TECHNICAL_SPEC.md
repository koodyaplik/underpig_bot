# Техническое задание: Telegram-бот отслеживания авиарейсов через Aviationstack

## 1. Назначение проекта

Разработать готового к эксплуатации Telegram-бота на Python, который:

- принимает явную команду с номером авиарейса;
- находит конкретный экземпляр рейса через Aviationstack API;
- сохраняет рейсы и пользовательские подписки в SQLite;
- опрашивает один физический рейс только один раз независимо от количества подписчиков;
- уведомляет пользователей только о значимых изменениях;
- надежно восстанавливает работу после перезапуска;
- экономно и предсказуемо расходует квоту Aviationstack;
- не допускает неконтролируемого платного перерасхода API.

Бот является информационным сервисом. Данные Aviationstack могут запаздывать или быть неполными. Бот не должен позиционироваться как источник данных для принятия решений, связанных с безопасностью полета или обязательным временем прибытия в аэропорт.

## 2. Зафиксированные продуктовые решения

### 2.1. Явный вызов команд

Поиск и включение отслеживания выполняются только через команду:

```text
/flight FV6106
```

или:

```text
/flight FV6106 2026-08-23
```

Для дальнего будущего рейса, когда Aviationstack требует аэропорт отправления:

```text
/flight FV6106 2026-09-15 GOJ
```

Также разрешено заранее указать аэропорт отправления, а дату затем выбрать кнопкой:

```text
/flight FV6106 GOJ
```

Обычное текстовое сообщение:

```text
FV6106
```

не должно запускать поиск, обращаться к Aviationstack или создавать подписку.

На обычный текст бот может отправить короткую подсказку с примером `/flight`, но такая подсказка должна быть ограничена rate limit, чтобы не создавать спам.

Если дата не передана в команде, бот не обращается к Aviationstack сразу. Он показывает inline-кнопки:

```text
Сегодня
Завтра
Послезавтра
Другая дата
Не знаю дату
Отмена
```

На кнопках быстрых дат дополнительно показываются число и месяц. «Сегодня» вычисляется в `BOT_DEFAULT_TIMEZONE`, а не по timezone сервера.

Кнопка «Другая дата» открывает inline-календарь на текущем месяце. Календарь должен:

- начинать неделю с понедельника;
- показывать русские названия месяца и дней недели;
- позволять переходить к предыдущему и следующему месяцу;
- иметь возврат к быстрому выбору;
- иметь кнопку отмены;
- укладывать каждый `callback_data` в ограничение Telegram 64 байта.

Выбор живет ограниченное время и привязан к Telegram user id. По умолчанию срок жизни — 15 минут. Повторная команда `/flight` инвалидирует незавершенный выбор этого пользователя. Aviationstack вызывается только после выбора точной даты либо кнопки «Не знаю дату».

### 2.2. Область использования Telegram

Первая версия поддерживает только личные чаты с ботом.

В группах, супергруппах, каналах и Telegram topics команды отслеживания не выполняются. Бот отвечает сообщением о необходимости открыть личный чат.

### 2.3. Язык

Пользовательские сообщения и названия статусов должны быть на русском языке.

Исходное значение `api_status` сохраняется в базе и логах без перевода.

### 2.4. Тариф Aviationstack

Для штатной эксплуатации требуется Aviationstack Basic или более высокий тариф.

Причины:

- целевая конфигурация предполагает 10 000 запросов в расчетном периоде;
- фильтрация исторических рейсов по `flight_date` и часть функций расписаний могут зависеть от тарифа;
- бесплатный тариф не подходит для постоянного polling нескольких рейсов.

Платный перерасход должен быть запрещен по умолчанию на уровне приложения.

### 2.5. Процессная модель

Поддерживается один процесс приложения и один экземпляр Telegram long polling.

Запуск нескольких реплик с одной SQLite-базой и одним Telegram-токеном не входит в первую версию. При необходимости горизонтального масштабирования хранилище и механизм блокировок должны быть пересмотрены отдельно.

### 2.6. Совместимость с распознаванием голосовых сообщений

Проект объединяется с существующим Underpig voice-ботом. Один Telegram-бот должен одновременно:

- распознавать входящие voice messages через `faster-whisper`;
- выполнять команды отслеживания рейсов;
- использовать общий Telegram-токен и общий SOCKS5 proxy;
- сохранять поддержку голосовых сообщений в личных чатах и группах;
- выполнять команды рейсов только в личном чате.

Модель Whisper загружается лениво при первом голосовом сообщении. Загрузка модели и распознавание выполняются через `asyncio.to_thread`, чтобы не блокировать Telegram polling, scheduler и notification worker. Одновременно допускается одна операция распознавания на процесс.

Голосовой файл хранится только во временном каталоге и удаляется после обработки. Максимальная длительность задается `MAX_DURATION`. Длинная расшифровка разбивается на сообщения не длиннее 4000 символов.

Переменная `TELEGRAM_PROXY` применяется ко всем обращениям к Telegram. Для обратной совместимости наряду с `TELEGRAM_BOT_TOKEN` принимается старое имя `BOT_TOKEN`.

## 4. Контракт с Aviationstack

### 4.1. Базовый адрес и авторизация

Основной endpoint:

```text
GET https://api.aviationstack.com/v1/flights
```

Авторизация:

```text
access_key=AVIATIONSTACK_API_KEY
```

API key передается только клиентом Aviationstack. Он не должен попадать в исходный код, Telegram-сообщения, обычные логи, traceback, URL в диагностических сообщениях и таблицу учета запросов.

При логировании URL значение `access_key` обязательно заменять на `[REDACTED]`.

### 4.2. Постоянный HTTP-клиент

Использовать один долгоживущий `httpx.AsyncClient` с connection pooling.

Явно настроить:

```text
connect timeout
read timeout
write timeout
pool timeout
maximum connections
maximum keep-alive connections
User-Agent
```

Клиент должен корректно закрываться при graceful shutdown.

### 4.3. Первоначальный поиск без даты

Если после команды:

```text
/flight FV6106
```

пользователь нажал «Не знаю дату», выполнить не более одного HTTP-запроса:

```text
GET /v1/flights?access_key=KEY&flight_iata=FV6106&limit=100&offset=0
```

Перед запросом проверить:

1. нет ли уже активного отслеживаемого рейса с таким номером;
2. нет ли свежего результата поиска в локальном кеше;
3. разрешает ли текущий бюджет квоты новый поиск;
4. не превышен ли пользовательский rate limit.

Не выполнять отдельные запросы за вчера, сегодня и завтра.

### 4.4. Поиск с явной датой

Для команды:

```text
/flight FV6106 2026-08-23
```

использовать:

```text
GET /v1/flights?access_key=KEY&flight_iata=FV6106&flight_date=2026-08-23&limit=100&offset=0
```

Явная дата не отменяет проверку нескольких сегментов. Если API вернул несколько маршрутов, пользователь должен выбрать конкретный вариант.

### 4.5. Дальние будущие рейсы

Endpoint Aviationstack `flightsFuture` предназначен для дат более чем через семь дней и требует аэропорт, дату и тип расписания.

Поэтому для такого поиска команда должна содержать IATA-код аэропорта отправления:

```text
/flight FV6106 2026-09-15 GOJ
```

Запрос строится логически так:

```text
GET /v1/flightsFuture
  ?access_key=KEY
  &date=2026-09-15
  &iataCode=GOJ
  &type=departure
  &airline_iata=FV
  &flight_number=6106
  &limit=100
  &offset=0
```

Если для выбранной даты Aviationstack требует аэропорт, а пользователь его не указал, бот не должен угадывать аэропорт и расходовать дополнительные запросы. Нужно показать корректный пример команды.

Ответ `flightsFuture` имеет другую структуру и должен обрабатываться отдельным адаптером. В частности, `data` может содержать вложенные массивы, а имена полей отличаются от `/v1/flights`.

Будущий рейс хранится как предварительно идентифицированный экземпляр. Пока real-time `/v1/flights` не начал возвращать этот рейс, использовать редкий polling. После появления real-time записи выполнить строгое сопоставление и перейти на обычную модель состояния.

Если конкретный тариф или endpoint не поддерживает будущие рейсы, бот должен вернуть понятное сообщение и не создавать фиктивную подписку.

### 4.6. Узкий запрос при polling

После идентификации экземпляра выполнять:

```text
GET /v1/flights
  ?access_key=KEY
  &flight_iata=FV6106
  &flight_date=2026-08-23
  &limit=100
  &offset=0
```

Запрос остается узким, но код не должен считать, что ответ содержит ровно один элемент.

### 4.7. Pagination и правило одного запроса

Ответ содержит:

```text
pagination.limit
pagination.offset
pagination.count
pagination.total
```

Главный приоритет проекта — экономия квоты, поэтому автоматический обход всех страниц для поиска одного номера рейса запрещен.

Правило:

1. запросить первую страницу с максимальным разрешенным тарифом `limit`;
2. обработать все записи страницы;
3. если `pagination.total > pagination.count` и однозначный экземпляр не найден, не запрашивать следующую страницу автоматически;
4. предложить пользователю уточнить дату или аэропорт отправления;
5. записать метрику `search_result_truncated`.

Каждая дополнительная страница является отдельным HTTP-запросом и отдельной единицей локального бюджета.

### 4.8. Структура real-time ответа

Типичный ответ содержит:

```text
pagination
data[]
```

Внутри элемента могут присутствовать:

```text
flight_date
flight_status

departure:
  airport
  timezone
  iata
  icao
  terminal
  gate
  delay
  scheduled
  estimated
  actual
  estimated_runway
  actual_runway

arrival:
  airport
  timezone
  iata
  icao
  terminal
  gate
  baggage
  delay
  scheduled
  estimated
  actual
  estimated_runway
  actual_runway

airline
flight
aircraft
live
```

Схема внешнего API считается недоверенной.

Любое необязательное поле и любой вложенный объект могут быть `null`, отсутствовать или иметь неожиданный тип. Частично заполненный элемент не должен приводить к падению всего worker.

Сохранять только конкретный raw flight item, а не всю страницу ответа с другими рейсами.

### 4.9. Статусы Aviationstack

Для `/v1/flights` поддержать:

```text
scheduled
active
landed
cancelled
incident
diverted
null
unknown string
```

Не придумывать API-статус `delayed`.

Неизвестный строковый статус сохранять как есть, логировать один раз в агрегированном виде и обрабатывать как нетерминальный неизвестный статус.

Внутреннее состояние задержки вычисляется отдельно.

### 4.10. Ошибки Aviationstack

Обрабатывать:

```text
timeout
network error
HTTP 429
HTTP 5xx
HTTP 401
HTTP 403
HTTP 404
невалидный JSON
API error object
validation_error
usage_limit_reached
rate_limit_reached
function_access_restricted
пустой data[]
частично заполненный flight object
```

Классификация:

- временные ошибки: timeout, network error, HTTP 429, HTTP 5xx;
- постоянная ошибка конфигурации: invalid key, inactive account, запрещенный тарифом endpoint;
- отсутствие конкретного рейса: успешный ответ с пустым `data[]` или без совпадающего экземпляра;
- поврежденный ответ: невалидный JSON или критически неполная структура.

Для HTTP 429 учитывать `Retry-After`, если он присутствует.

Ошибка авторизации должна открывать глобальный circuit breaker Aviationstack. Нельзя повторять одинаковый заведомо неуспешный запрос для каждого рейса.

Пользователям не отправлять сообщение при каждом HTTP-сбое. Системные проблемы писать в лог и один раз сообщать администраторам.

## 5. Telegram-команды

Поддержать:

```text
/start
/help
/flight <flight_iata> [YYYY-MM-DD] [departure_iata]
/flights
/stop [subscription_id]
/delete_me
```

### 5.1. `/start`

Кратко объясняет назначение бота, ограничения источника данных и показывает примеры явных команд.

Команда не обращается к Aviationstack.

### 5.2. `/help`

Показывает синтаксис команд и примеры:

```text
/flight FV6106
/flight FV6106 2026-08-23
/flight FV6106 2026-09-15 GOJ
/flight FV6106 GOJ
/flights
/stop
```

Команда не обращается к Aviationstack.

### 5.3. `/flight`

Валидирует аргументы, ищет рейс, при необходимости предлагает варианты и создает подписку.

Команда без номера рейса возвращает помощь и не обращается к API.

Команда с номером, но без даты, создает краткоживущую сессию выбора даты и показывает быстрые кнопки. Само получение этой команды не обращается к API. После выбора точной даты выполняется поиск с `flight_date`; после выбора «Не знаю дату» — один поиск без `flight_date`.

Команда с датой выполняет поиск сразу, без промежуточного календаря. Вариант `/flight FV6106 GOJ` сохраняет аэропорт отправления в сессии и затем предлагает выбрать дату кнопками.

Номер нормализуется в верхний регистр. Не удалять ведущие нули номера.

Минимально допустимый формат:

```text
двухсимвольный IATA-код авиакомпании
от одной до четырех цифр номера
опциональная буквенная суффиксная часть, если ее принимает API
```

В пользовательском интерфейсе основной формат должен быть компактным: `FV6106`.

### 5.4. `/flights`

Показывает только подписки текущего пользователя:

- идентификатор подписки;
- номер рейса;
- дату;
- маршрут;
- текущее состояние;
- время последной успешной проверки;
- кнопку остановки.

Список должен иметь Telegram-пагинацию, если подписок больше размера одной страницы.

Команда не обращается к Aviationstack.

### 5.5. `/stop`

Варианты:

```text
/stop
/stop 123
```

`/stop` без аргумента показывает активные подписки с inline-кнопками.

`/stop 123` отключает только подписку с идентификатором `123`, если она принадлежит текущему пользователю.

Остановка по одному номеру вроде `/stop FV6106` не поддерживается, поскольку один пользователь может отслеживать несколько дат или маршрутов этого номера.

Если удалена последняя активная подписка на физический рейс:

1. дальнейшие запросы Aviationstack для него прекращаются;
2. `tracking_state` переводится в `paused_no_subscribers`;
3. raw данные сохраняются до истечения retention period;
4. повторная подписка может реактивировать рейс после проверки актуальности состояния.

### 5.6. `/delete_me`

Требует явного подтверждения inline-кнопкой.

После подтверждения:

- деактивирует все подписки пользователя;
- удаляет пользовательские pending selections;
- удаляет или анонимизирует Telegram user/chat identifiers в соответствии с политикой хранения;
- не удаляет общую запись физического рейса, если на нее подписаны другие пользователи.

## 6. Ограничение злоупотреблений

До любого внешнего запроса проверить:

```text
per-user command rate limit
per-user active subscriptions limit
global active flights limit
quota admission control
optional allowlist
```

Минимальная конфигурация:

```text
MAX_ACTIVE_SUBSCRIPTIONS_PER_USER=10
MAX_ACTIVE_TRACKED_FLIGHTS=100
FLIGHT_COMMANDS_PER_USER_PER_MINUTE=3
```

Повторная команда того же пользователя для уже существующей подписки должна быть идемпотентной и не расходовать API quota.

## 7. Первоначальный выбор конкретного рейса

### 7.1. Общие правила

Запрещено использовать `data[0]` как гарантированно правильный результат.

Алгоритм должен быть чистой тестируемой функцией:

```python
select_flight_candidates(items, query, now)
```

### 7.2. Фильтрация

Для каждого элемента:

1. безопасно извлечь `flight.iata`;
2. нормализовать регистр и допустимые разделители;
3. оставить только точные совпадения с введенным номером;
4. отбросить элементы без минимальной идентификационной информации;
5. не полагаться на порядок массива.

### 7.3. Выбор без даты

Для каждого кандидата определить текущую календарную дату в `departure.timezone`.

Приоритет:

1. рейс со статусом `active` текущей даты;
2. нетерминальный рейс текущей даты, ближайший по актуальному времени вылета;
3. завершенный рейс текущей даты, если других вариантов нет;
4. иные даты не выбирать автоматически.

Под нетерминальным понимается рейс, который не имеет статуса `landed` или `cancelled` и не завершен внутренней state machine.

Если несколько разных маршрутов или сегментов остаются подходящими, показать inline-кнопки с:

```text
номер рейса
дата
departure_iata -> arrival_iata
локальное время вылета
статус
```

Автоматически выбирать один маршрут из нескольких запрещено.

### 7.4. Выбор с датой

Отфильтровать `flight_date` по точному совпадению.

Если осталось несколько сегментов, показать варианты маршрута.

Если осталось несколько элементов одного маршрута, выбрать ближайший к указанной дате и ожидаемому scheduled wall-clock времени, но только после детерминированной сортировки.

### 7.5. Pending selection

Варианты выбора сохранять в таблице `pending_selections` с TTL, например 15 минут.

Callback-кнопка должна содержать непрозрачный короткий идентификатор, а не весь flight JSON.

При выборе проверить:

- принадлежность текущему пользователю;
- срок действия;
- что вариант не был использован;
- что соответствующая подписка еще не существует.

После истечения TTL предложить повторить `/flight`. Не выполнять новый запрос автоматически по старой кнопке.

## 8. Идентификатор экземпляра и повторное сопоставление

### 8.1. Неизменяемый identity

Логический identity строить минимум из:

```text
requested_flight_iata
flight_date
departure_iata
arrival_iata
identity_scheduled_departure_local
departure_timezone, если она известна
```

`identity_scheduled_departure_local` фиксируется при создании рейса и не изменяется при последующих обновлениях API.

Текущее `scheduled_departure` хранится отдельно и может обновляться без создания новой строки.

Создать стабильный `instance_key`, например SHA-256 от канонического identity, и уникальный индекс по нему.

### 8.2. Повторное сопоставление при polling

Использовать отдельную чистую функцию:

```python
match_tracked_instance(candidates, persisted_identity)
```

Алгоритм:

1. точное совпадение введенного `flight_iata`;
2. точное совпадение `flight_date`;
3. точное совпадение departure и arrival IATA;
4. совпадение или минимальное отклонение scheduled wall-clock времени от identity;
5. детерминированный tie-breaker;
6. запрет переключения на другой маршрут или сегмент.

Если совпадение не найдено:

- не затирать старое состояние;
- увеличить `consecutive_not_found`;
- применить backoff;
- сохранить диагностическую информацию без API key;
- не считать рейс автоматически завершенным после одного пустого ответа.

## 9. Обработка времени Aviationstack

### 9.1. Изолированный адаптер

Создать отдельный модуль и функцию:

```python
parse_aviationstack_time(raw_timestamp, airport_timezone)
```

Результат должен содержать:

```text
raw_timestamp
airport_timezone
local_datetime
utc_datetime
parse_method
confidence
error
```

### 9.2. Wall-clock quirk

Aviationstack может возвращать локальное wall-clock время аэропорта со смещением `+00:00` или `Z`.

При настроенном режиме `wall_clock` адаптер должен:

1. взять календарную дату и время из строки, не переводя их через `astimezone()`;
2. проверить `departure.timezone` или `arrival.timezone` через `ZoneInfo`;
3. создать локальный timezone-aware `datetime` из wall-clock компонентов;
4. только затем вычислить UTC;
5. сохранить raw значение и способ интерпретации.

Пример:

```text
raw:        2026-08-23T13:15:00+00:00
timezone:   Europe/Moscow
local:      2026-08-23T13:15:00+03:00
UTC:        2026-08-23T10:15:00+00:00
method:     wall_clock_airport_timezone
confidence: high
```

### 9.3. Режим интерпретации

Конфигурация:

```text
AVIATIONSTACK_TIME_MODE=wall_clock
```

Допустимые внутренние режимы:

```text
wall_clock
iso8601
```

Режим не должен автоматически меняться от ответа к ответу без явной конфигурации. Изменение режима требует contract tests на сохраненных реальных fixtures.

### 9.4. Fallback

Если timezone отсутствует или некорректна:

1. не назначать произвольную timezone;
2. если raw содержит корректное смещение, разрешается сохранить абсолютное время по этому смещению с `confidence=low` и `parse_method=raw_offset_fallback`;
3. если надежно получить UTC невозможно, сохранить `utc_datetime=null`;
4. использовать консервативный polling относительно `now`, а не ошибочное вычисленное время;
5. не показывать пользователю выдуманную timezone;
6. записать агрегированное предупреждение в лог.

### 9.5. DST

Отдельно обработать неоднозначное и несуществующее локальное время при переходе DST.

Если raw offset позволяет выбрать корректный `fold`, использовать его. Если данных недостаточно, не скрывать неоднозначность: установить низкую confidence, залогировать и применить безопасный fallback.

### 9.6. Хранение времени

Поля, участвующие в сравнении и scheduler, хранить как UTC Unix epoch integer.

Отдельно сохранять:

```text
raw timestamp
локальный wall-clock ISO text
IANA timezone name
UTC epoch
parse method
confidence
```

Не смешивать SQLite `CURRENT_TIMESTAMP`, ISO-строки с `T`, строки с `Z` и локальное время в одном сравниваемом столбце.

## 10. Нормализованное состояние

Не сравнивать целиком raw JSON.

Создать версионированный нормализованный объект:

```text
schema_version
api_status

scheduled_departure
estimated_departure
actual_departure
departure_delay_minutes
departure_terminal
departure_gate

scheduled_arrival
estimated_arrival
actual_arrival
arrival_delay_minutes
arrival_terminal
arrival_gate
arrival_baggage

aircraft_registration
source_updated_at
fetched_at
```

Нормализовать:

- пустые строки в `null`;
- пробелы по краям;
- регистр gate и terminal, если это безопасно;
- числа задержки в integer;
- timestamps через адаптер Aviationstack;
- неизвестные вложенные типы без исключения всего ответа.

`schema_version` нужен, чтобы изменение нормализатора после деплоя не создало ложные пользовательские уведомления.

## 11. Вычисление задержки

`delayed` не является значением `api_status`.

До фактического вылета эффективная задержка отправления определяется в порядке приоритета:

1. `estimated_departure - scheduled_departure`, если оба времени надежны;
2. `departure.delay`, если это корректное неотрицательное число;
3. отсутствие вычислимой задержки.

После фактического вылета:

1. `actual_departure - scheduled_departure`, если оба времени надежны;
2. `departure.delay` как fallback.

Аналогично для прибытия.

Отрицательное значение означает раннее событие, а не задержку. Для `is_delayed` использовать только значение больше нуля.

Если API delay и вычисленная задержка существенно расходятся, выбрать вычисленную по надежным timestamps, сохранить расхождение в диагностике и не отправлять два отдельных уведомления.

## 12. Обнаружение значимых изменений

Создать чистую функцию:

```python
diff_flight_state(old_state, new_state, policy) -> list[DomainEvent]
```

### 12.1. Всегда значимые изменения

```text
api_status -> active
api_status -> landed
api_status -> cancelled
api_status -> incident
api_status -> diverted
появление actual departure
появление actual arrival
изменение departure gate
изменение departure terminal
изменение arrival gate
изменение arrival terminal
изменение baggage
```

### 12.2. Изменения времени и задержки

Уведомлять об изменении estimated или delay, если модуль изменения не меньше:

```text
NOTIFICATION_TIME_CHANGE_THRESHOLD_MINUTES=5
```

Порог не применяется к фактическому времени и терминальным статусам.

### 12.3. Null-переходы

Правила:

- первичная загрузка состояния не генерирует события `null -> value`; пользователь получает одну карточку подписки;
- при последующих успешных polling `null -> value` считается изменением;
- `value -> null` не уведомляет по умолчанию, чтобы не спамить из-за временно неполного ответа;
- исчезновение уже назначенного gate, terminal или baggage можно уведомлять только после двух последовательных подтверждений;
- старое ненулевое значение не затирать одним частично заполненным ответом без специального подтверждения.

### 12.4. Объединение событий

Все изменения одного рейса, найденные в одном polling, объединять в одно Telegram-сообщение.

Например изменение статуса, gate и estimated departure не должно создавать три последовательных сообщения.

### 12.5. Регрессии статуса

Подозрительная регрессия вроде `active -> scheduled` не должна немедленно отправляться пользователю и затирать подтвержденное состояние.

Обычную регрессию подтвердить двумя последовательными одинаковыми ответами.

Переходы в `cancelled`, `incident`, `diverted` и `landed` считаются приоритетными и не требуют второго подтверждения.

Терминальное внутреннее состояние нельзя автоматически вернуть в активное без отдельной явно реализованной политики.

## 13. Формат пользовательских сообщений

### 13.1. Общие правила

- использовать русский язык;
- экранировать все строки Aviationstack для выбранного Telegram parse mode;
- показывать IATA-коды маршрута вместе с названиями аэропортов;
- для вылета использовать локальное время аэропорта отправления;
- для прилета использовать локальное время аэропорта прибытия;
- показывать календарную дату каждого события, если рейс ночной или даты различаются;
- не показывать пользователю технические поля, confidence и raw JSON;
- не обещать мгновенное обновление.

Перевод статусов:

```text
scheduled -> запланирован
active -> в полете
landed -> прибыл
cancelled -> отменен
incident -> инцидент
diverted -> направлен в другой аэропорт
null/unknown -> нет подтвержденного статуса
```

### 13.2. Подписка включена

```text
FV6106
Нижний Новгород (GOJ) -> Санкт-Петербург (LED)
23.08.2026

Вылет: 13:15 Europe/Moscow
Прилет: 15:10 Europe/Moscow
Статус: запланирован

Отслеживание включено.
Номер подписки: 123
```

### 13.3. Изменение вылета

```text
FV6106 — изменилось время вылета

23.08.2026
13:15 -> 14:05 Europe/Moscow
Задержка: 50 минут
```

### 13.4. Gate и terminal

```text
FV6106 — назначен выход

Аэропорт: GOJ
Терминал: 1
Выход: 12
```

### 13.5. Вылет

```text
FV6106 — вылетел

Фактический вылет:
23.08.2026 14:02 Europe/Moscow

Ожидаемое прибытие:
23.08.2026 15:47 Europe/Moscow
```

### 13.6. Прибытие

Если baggage уже известно:

```text
FV6106 — прибыл

Фактическое прибытие:
23.08.2026 15:43 Europe/Moscow

Задержка прибытия: 33 минуты
Выдача багажа: 4

Отслеживание завершено.
```

Если baggage еще нет и включена post-landing фаза:

```text
FV6106 — прибыл

Фактическое прибытие:
23.08.2026 15:43 Europe/Moscow

Рейс прибыл. Бот еще некоторое время проверит информацию о выдаче багажа.
```

### 13.7. Недостоверное завершение

Если API не подтвердил `landed`:

```text
FV6106

Новых подтвержденных данных после расчетного времени прибытия нет.
Автоматическое отслеживание завершено без подтверждения посадки.
```

Нельзя писать «рейс приземлился», если API этого достоверно не подтвердил.

## 14. Надежная доставка уведомлений

### 14.1. Transactional outbox

Обновление рейса и создание пользовательского события выполнять в одной SQLite-транзакции:

1. сохранить новое нормализованное состояние;
2. увеличить `state_version`;
3. создать `notification_event`;
4. создать delivery для каждой активной подписки;
5. зафиксировать транзакцию;
6. только после этого отправлять Telegram-сообщения отдельным worker.

Уникальные ограничения должны предотвращать повторное создание одинакового события и delivery.

### 14.2. Гарантия

Целевая гарантия — at-least-once с best-effort дедупликацией.

Абсолютное exactly-once невозможно гарантировать, если Telegram принял сообщение, но сетевое подтверждение потерялось. Такой редкий риск дубля допустим, потеря сохраненного события — нет.

### 14.3. Ошибки Telegram

Обрабатывать:

```text
429 Retry-After
timeout
network error
5xx
403 bot blocked
chat not found
невалидный формат сообщения
```

Для временных ошибок использовать retry с `next_attempt_at`.

При `bot blocked` или `chat not found` деактивировать подписки этого чата и не повторять бесконечно.

Ошибка форматирования должна переводить delivery в окончательную ошибку, логироваться и отправлять административный сигнал без раскрытия пользовательских данных.

## 15. Динамический polling

Создать чистую функцию:

```python
calculate_next_check(flight, now, quota_state) -> PollDecision
```

`PollDecision` содержит:

```text
next_check_at
reason
priority
uses_reserve
```

### 15.1. Базовое время вылета

Использовать в порядке приоритета:

```text
estimated_departure
scheduled_departure
```

Если время недостоверно или отсутствует, использовать отдельную консервативную policy, а не выдуманное значение.

### 15.2. До вылета

Начальная policy:

```text
более 7 дней:
раз в 24 часа через future schedule endpoint

24 часа - 7 дней:
раз в 6 часов

12-24 часа:
раз в 3 часа

6-12 часов:
раз в 1 час

2-6 часов:
раз в 30 минут

30 минут - 2 часа:
раз в 10 минут

менее 30 минут:
раз в 5 минут
```

Если estimated departure изменился, следующий polling рассчитывать относительно нового estimated времени.

### 15.3. После вылета

При `api_status=active`:

```text
до расчетного прибытия более 30 минут:
раз в 10 минут

до расчетного прибытия менее 30 минут:
раз в 5 минут

после расчетного прибытия:
раз в 5 минут до grace period
```

### 15.4. Неизвестный статус

При `api_status=null` или неизвестном статусе использовать положение рейса относительно надежных scheduled/estimated времен.

Не выводить искусственный API-статус.

Если надежных времен нет, применять backoff и общий максимальный возраст отслеживания.

### 15.5. Cancelled, incident и diverted

При получении `cancelled`:

1. создать приоритетное уведомление;
2. сохранить состояние;
3. перевести рейс в `finished_cancelled`;
4. прекратить polling.

«Немедленно» означает при ближайшем успешном polling, а не раньше получения данных от Aviationstack.

При `incident`:

- создать приоритетное уведомление;
- продолжить polling по интервалу не чаще пяти минут;
- применить общий предел длительности.

При `diverted`:

- создать приоритетное уведомление;
- продолжить polling;
- использовать отдельный `DIVERTED_MAX_TRACKING_HOURS`;
- не считать старое scheduled arrival достаточным основанием для бесконечного агрессивного polling.

### 15.6. Landed и baggage

При `landed` немедленно создать уведомление о прибытии.

Если baggage уже известно или post-landing tracking выключен, перевести рейс в `finished_landed`.

Если baggage отсутствует и post-landing tracking включен:

```text
tracking_state=post_landing
```

Проверять раз в 10 минут, но не дольше:

```text
POST_LANDING_BAGGAGE_GRACE_MINUTES=30
```

После появления baggage отправить одно обновление и завершить отслеживание. После истечения grace period завершить без сообщения об ошибке.

### 15.7. Защита от бесконечного polling

Основной критерий завершения:

```text
api_status=landed
```

Fallback:

```text
now > estimated_arrival + ARRIVAL_STALE_GRACE_HOURS
```

или при отсутствии estimated:

```text
now > scheduled_arrival + ARRIVAL_STALE_GRACE_HOURS
```

По умолчанию:

```text
ARRIVAL_STALE_GRACE_HOURS=6
```

Если подтверждения нет, установить:

```text
tracking_state=finished_stale
finished_reason=stale_after_arrival
```

и отправить нейтральное финальное сообщение.

Также должен существовать абсолютный `MAX_TRACKING_AGE_HOURS`, применяемый при полностью отсутствующих временах.

### 15.8. Jitter

Добавлять детерминированный jitter до 5% интервала, основанный на `flight_id`, чтобы после рестарта решения оставались воспроизводимыми.

Для рейсов менее чем за 30 минут до события задержка из-за jitter не должна превышать 30 секунд.

## 16. Backoff

Для временных ошибок использовать интервалы:

```text
5 минут
15 минут
30 минут
60 минут
```

После достижения максимума продолжать с интервалом 60 минут, но учитывать близость рейса и quota state.

HTTP 429 с корректным `Retry-After` имеет приоритет над стандартной последовательностью.

При успехе сбрасывать `consecutive_failures` и `consecutive_not_found`.

Одна ошибка не удаляет рейс, не меняет его на landed и не порождает пользовательское уведомление.

## 17. Scheduler и защита от двойных запросов

### 17.1. Выбор due flights

Один scheduler просыпается примерно раз в 30 секунд.

Он выбирает только состояния, разрешающие polling:

```sql
SELECT id
FROM flights
WHERE tracking_state IN (
  'scheduled',
  'active',
  'incident',
  'diverted',
  'post_landing',
  'future_scheduled'
)
  AND next_check_at_epoch <= :now
  AND (lease_until_epoch IS NULL OR lease_until_epoch < :now)
ORDER BY polling_priority DESC, next_check_at_epoch ASC
LIMIT :batch_size;
```

### 17.2. Lease

Каждый рейс атомарно захватывается через:

```text
lease_owner
lease_until_epoch
```

Только владелец действующего lease имеет право выполнять запрос и сохранять результат.

Нельзя держать SQLite write transaction открытой во время HTTP-запроса.

Если процесс завершился аварийно, просроченный lease автоматически становится доступен следующему циклу.

### 17.3. Ограничение параллелизма

Конфигурация:

```text
SCHEDULER_TICK_SECONDS=30
SCHEDULER_BATCH_SIZE=20
AVIATIONSTACK_MAX_CONCURRENCY=5
FLIGHT_LEASE_SECONDS=120
```

Использовать общий `asyncio.Semaphore` для запросов Aviationstack.

### 17.4. Перезапуск без request storm

При старте:

1. найти активные рейсы с просроченным `next_check_at`;
2. назначить ближайшие проверки с учетом приоритета;
3. распределить их по небольшому стартовому окну;
4. не запускать все запросы одновременно;
5. не тратить reserve на дальние рейсы.

## 18. Контроль квоты Aviationstack

### 18.1. Учет запросов

Каждая фактическая попытка HTTP-запроса записывается до или сразу после отправки.

Минимальные поля:

```text
id
request_started_at_epoch
request_finished_at_epoch
endpoint_name
flight_id
trigger_type
success
http_status
api_error_code
attempted_cost
duration_ms
created_at_epoch
```

Не хранить полный URL с API key.

Локальная безопасная модель считает каждую отправленную попытку как одну единицу бюджета, даже если поставщик может не тарифицировать часть ошибок. Это консервативно защищает от overage.

### 18.2. Конфигурация бюджета

```text
AVIATIONSTACK_MONTHLY_REQUEST_LIMIT=10000
AVIATIONSTACK_REQUEST_RESERVE=500
AVIATIONSTACK_HARD_REQUEST_CAP=10000
AVIATIONSTACK_ALLOW_OVERAGE=false
AVIATIONSTACK_BILLING_CYCLE_DAY=1
```

Если реальный billing cycle не начинается первого числа, значение обязательно изменить.

### 18.3. Приоритеты

```text
1. active, incident и diverted
2. менее 30 минут до актуального события
3. менее 2 часов до актуального события
4. post_landing в пределах короткого grace period
5. остальные рейсы текущего дня
6. дальние рейсы
7. новые пользовательские поиски
```

### 18.4. Reserve и hard cap

Обычный бюджет:

```text
monthly_limit - reserve
```

После его исчерпания reserve разрешено использовать только приоритетам 1-4.

После достижения hard cap запрещены все новые запросы, если `ALLOW_OVERAGE=false`.

Приложение должно:

- перевести затронутые рейсы в `suspended_quota`;
- не создавать новые подписки, требующие API-запроса;
- один раз уведомить администратора;
- при необходимости один раз нейтрально уведомить подписчиков о временной приостановке;
- автоматически возобновить работу в новом billing cycle.

### 18.5. Admission control

Перед созданием нового физического отслеживания оценить ожидаемое число запросов до завершения рейса на основе polling policy.

Если ожидаемая стоимость не помещается в доступный обычный бюджет, отказать до внешнего запроса или до создания подписки с понятным сообщением.

Новый пользователь существующего физического рейса не увеличивает прогноз API-запросов и может быть подписан без расходования квоты, если сохраненное состояние достаточно свежее.

## 22. Graceful startup и shutdown

### Startup

Порядок:

1. загрузить и строго проверить конфигурацию;
2. проверить наличие timezone database;
3. открыть SQLite и применить миграции;
4. восстановить circuit breaker и quota state;
5. распределить overdue flights;
6. запустить scheduler и notification worker;
7. запустить Telegram long polling;

При неверном Telegram token, Aviationstack key format или недоступной базе завершить startup с понятной ошибкой без вывода секрета.

### Shutdown

При SIGTERM/SIGINT:

1. прекратить принимать новые Telegram updates;
2. прекратить брать новые scheduler leases;
3. дать выполняющимся операциям ограниченное время на завершение;
4. корректно освободить или дождаться истечения leases;
5. закрыть HTTP client;
6. закрыть SQLite connections;
7. завершить процесс до Docker stop timeout.

## 27. Критерии приемки

Проект считается готовым, если одновременно выполняются условия:

1. Обычный текст с номером рейса не вызывает API и не создает подписку.
2. `/flight FV6106` до выбора даты показывает кнопки и не вызывает API.
3. Быстрые даты и inline-календарь создают поиск только после однократного выбора пользователя.
4. `/flight` не выбирает `data[0]` вслепую.
5. Несколько сегментов показываются пользователю для явного выбора.
6. Polling всегда сопоставляет сохраненный экземпляр и не переключается на другой маршрут.
7. Один физический рейс опрашивается один раз независимо от количества подписчиков.
8. Значимое изменение сохраняется в outbox до отправки Telegram.
9. Рестарт между сохранением и отправкой не приводит к потере события.
10. Динамический polling использует новое estimated время.
11. Cancelled и landed прекращают обычный polling согласно state machine.
12. Landed без baggage не противоречит post-landing policy.
13. Неполные данные не приводят к бесконечному polling.
14. API key и Telegram token отсутствуют в логах и репозитории.
15. Hard quota запрещает запросы сверх лимита при отключенном overage.
16. Последняя отписка прекращает расходование Aviationstack quota для рейса.
17. После рестарта контейнера активные рейсы восстанавливаются без request storm.
18. Все обязательные unit и integration tests проходят.
19. Docker healthcheck отражает работоспособность локальных worker и базы.
20. Приложение корректно завершает работу по SIGTERM.
