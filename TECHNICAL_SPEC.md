# Техническое задание: Telegram-бот отслеживания рейсов через FlightAware AeroAPI

## 1. Назначение

Бот должен:

- явно запускать поиск только по команде `/flight`;
- предлагать удобный выбор даты в Telegram;
- находить конкретный физический рейс через FlightAware AeroAPI;
- отправлять начальное состояние и последующие изменения в тот чат, где создана подписка;
- работать в личных чатах, группах и супергруппах;
- опрашивать один физический рейс один раз независимо от числа подписчиков;
- сохранять изменения и доставки в SQLite до отправки в Telegram;
- восстанавливаться после перезапуска без потери подписок и событий;
- сохранять существующую функцию локального распознавания голосовых сообщений.

Бот является информационным сервисом. Данные провайдера могут быть неполными или запаздывать и не заменяют официальную информацию авиакомпании или аэропорта.

## 2. Пользовательский интерфейс

### 2.1. Явный запуск

Основная команда:

```text
/flight FV6106
```

Обычный текст:

```text
FV6106
```

не вызывает AeroAPI и не создает подписку. В личном чате бот может не чаще одного раза в 30 секунд подсказать формат `/flight FV6106`.

Допускается прямое указание даты:

```text
/flight FV6106 2026-08-24
```

Другие аргументы и произвольные сокращенные команды не поддерживаются.

### 2.2. Выбор даты

Если дата не указана, бот показывает inline-кнопки:

- «Сегодня»;
- «Завтра»;
- «Послезавтра»;
- «Другая дата»;
- «Отмена».

«Другая дата» открывает inline-календарь с русскими названиями месяцев, днями недели, переходом между месяцами и возвратом к быстрым кнопкам.

Разрешенный диапазон: от текущей даты в `BOT_DEFAULT_TIMEZONE` до 363 дней вперед. Прошлые и слишком дальние дни видны, но неактивны. Сервер повторно проверяет диапазон после callback и не доверяет данным кнопки.

Сессия выбора:

- хранится в SQLite;
- привязана к пользователю и чату;
- одноразовая;
- имеет TTL `PENDING_SELECTION_TTL_MINUTES`;
- новая сессия заменяет предыдущую сессию того же пользователя только в том же чате.

### 2.3. Несколько вариантов

Если найдены разные маршруты или сегменты одного номера, бот показывает отдельную кнопку для каждого варианта:

```text
GOJ → LED · 2026-08-24 · 13:15
```

Нельзя автоматически выбирать первый элемент ответа.

### 2.4. Группы

Подписка содержит одновременно:

- Telegram user ID владельца;
- Telegram chat ID места доставки.

Команды `/flights` и `/stop` показывают и изменяют только подписки пользователя в текущем чате. Если несколько пользователей одной группы подписаны на один рейс, физический рейс опрашивается один раз, а событие доставляется в группу один раз.

## 3. Контракт FlightAware AeroAPI

Актуальная версия, использованная при реализации: AeroAPI 4.30.0.

Базовый URL:

```text
https://aeroapi.flightaware.com/aeroapi
```

Авторизация:

```http
x-apikey: <FLIGHTAWARE_AEROAPI_KEY>
```

Имя пользователя FlightAware для авторизации не используется.

### 3.1. Текущие и ближайшие рейсы

Endpoint:

```http
GET /flights/{ident}?ident_type=designator&max_pages=1
```

В `{ident}` передается нормализованный IATA designator, например `FV6106`. AeroAPI рекомендует ICAO designator для устранения неоднозначности, но интерфейс бота принимает привычный пользователю IATA-номер и явно задает `ident_type=designator`.

Без `start/end` endpoint возвращает примерно 14 дней недавних и запланированных рейсов. Бот нормализует все элементы и фильтрует выбранную дату по часовому поясу аэропорта отправления.

Параметры `start/end` намеренно не используются для первичного поиска: их допустимый диапазон ограничен 10 днями назад и 2 днями вперед, а UTC-границы могут не совпадать с локальной датой вылета.

### 3.2. Дальнее расписание

Для даты дальше двух дней:

```http
GET /schedules/{date_start}/{date_end}
    ?airline=FV
    &flight_number=6106
    &include_codeshares=true
    &include_regional=true
    &max_pages=1
```

Документация AeroAPI допускает расписания до одного года вперед и диапазон запроса не более трех недель. Для выбранной даты бот запрашивает окно от предыдущего дня до двух дней после выбранного, чтобы покрыть все часовые пояса, затем выполняет точную локальную фильтрацию.

Если тариф не поддерживает `/schedules`, пользователь получает понятное сообщение, а бот не открывает глобальный circuit breaker.

### 3.3. Метаданные аэропортов

Endpoint:

```http
GET /airports/{id}
```

Он используется для получения названия и IANA timezone аэропорта у элементов расписания. Ответ кэшируется в `service_state` по коду аэропорта. Повторный запрос для уже известного аэропорта не выполняется.

Если метаданные временно недоступны, допускается UTC fallback. Ошибка отдельного аэропорта не должна уничтожать весь ответ расписания.

### 3.4. Повторный опрос

Из ответа сохраняется `fa_flight_id`. После перехода рейса в ближайшее окно polling использует:

```http
GET /flights/{fa_flight_id}?ident_type=fa_flight_id&max_pages=1
```

Это основной идентификатор конкретного физического рейса. Для старых записей базы без `fa_flight_id` используется fallback по designator; после успешного ответа идентификатор сохраняется в `latest_candidate_json`.

При диверсии AeroAPI может вернуть несколько элементов с одинаковым `fa_flight_id`. Тогда дополнительно учитываются сохраненный маршрут и исходное время вылета.

### 3.5. Логирование запроса

Каждый запрос записывается на INFO:

```text
AeroAPI request: GET https://aeroapi.flightaware.com/aeroapi/...
```

Лог содержит метод, endpoint и query string. Значение `x-apikey` не логируется, потому что ключ передается заголовком, а не URL. Форматтер дополнительно удаляет `FLIGHTAWARE_AEROAPI_KEY`, `AEROAPI_KEY` и `x-apikey`, если они случайно попадут в сообщение.

При `AEROAPI_EXTENDED_LOGGING=true` после каждого запроса дополнительно записываются HTTP-статус и полный необработанный ответ AeroAPI, включая ответы с ошибкой. По умолчанию режим отключен из-за объема логов.

## 4. Нормализация данных

### 4.1. Идентификаторы

Сохраняются:

- введенный пользователем IATA designator;
- `ident_iata` или соответствующий элемент `codeshares_iata`;
- `fa_flight_id`;
- маршрут;
- локальная дата;
- исходное локальное время вылета.

Код должен поддерживать буквенно-цифровые IATA-префиксы, например `5N123`.

### 4.2. Время

AeroAPI передает времена в ISO 8601, обычно в UTC. Функция `parse_aeroapi_time`:

1. строго разбирает ISO 8601;
2. переводит значение в UTC epoch;
3. переводит его в IANA timezone аэропорта;
4. сохраняет raw, timezone, local ISO, UTC epoch, метод и уверенность;
5. не падает на `null`, неверном типе или неизвестной timezone.

Для вылета используются gate times `scheduled_out`, `estimated_out`, `actual_out` с fallback на runway times `scheduled_off`, `estimated_off`, `actual_off`.

Для прибытия используются `scheduled_in`, `estimated_in`, `actual_in` с fallback на `scheduled_on`, `estimated_on`, `actual_on`.

Фазы движения различаются отдельно: `actual_out` означает отправление от гейта, `actual_off` —
фактический взлет, `actual_on` — посадку на полосу, `actual_in` — прибытие к гейту. Появление
`actual_off` и `actual_on` всегда создает отдельное уведомление. Значения `departure_delay` и
`arrival_delay` не используются как доказательство наступления этих событий.

### 4.3. Статус

Внутренние статусы:

```text
scheduled
active
landed
cancelled
diverted
incident
null
```

Приоритет определения:

1. `cancelled=true` → `cancelled`;
2. `diverted=true` → `diverted`;
3. имеется `actual_in` или `actual_on` → `landed`;
4. имеется `actual_out` или `actual_off` → `active`;
5. распознаваемое значение `status`;
6. иначе `scheduled`.

Внутренний статус используется только для логики отслеживания. В сообщениях пользователю
показывается исходное поле `status` из AeroAPI без перевода и переименования. Если источник
не передал `status` (например, для далекого расписания), бот использует внутренний статус как
резервное отображение.

Поле `status` не разбирается для переходов автомата отслеживания: FlightAware документирует
его как динамический, локализуемый текст для человека. Изменение этого поля при этом является
самостоятельным событием для уведомления. Для записей, созданных до сохранения `provider_status`,
предыдущее значение восстанавливается из сохраненного сырого ответа AeroAPI.
Если такая старая запись все еще имеет внутренний статус `active`, но расчетное прибытие уже
прошло, текущий исходный статус отправляется один раз даже без доступной истории изменений.

`departure_delay` и `arrival_delay` AeroAPI считаются секундами и переводятся в минуты.
Отрицательные значения пользователю не показываются числами со знаком: бот пишет «раньше на
N минут». Положительные значения отображаются как задержка, нулевые — как движение по
расписанию. До фактического события используется прогнозная формулировка «Ожидается…», после
него — «Вылетел…» или «Прилетел…».

## 5. Подписки, состояние и polling

Таблица физического рейса отделена от подписок. Instance key строится по номеру, дате, маршруту, времени и timezone для совместимости с существующей базой. `fa_flight_id` используется при сетевом сопоставлении.

Состояния отслеживания:

```text
future_scheduled
scheduled
active
diverted
incident
post_landing
finished_landed
finished_cancelled
finished_stale
suspended_quota
suspended_provider
paused_no_subscribers
```

Дальний рейс проверяется редко. В пределах семи дней частота постепенно увеличивается. Активный рейс проверяется каждые 10 минут, возле расчетного прибытия — каждые 5 минут. После посадки допускается короткий период проверки багажа.

Последняя отписка переводит рейс в `paused_no_subscribers` и прекращает расходование AeroAPI.

## 6. Значимые изменения

Уведомление создается при изменении:

- статуса;
- estimated времени не менее чем на заданный порог;
- actual времени;
- задержки не менее чем на порог;
- терминала;
- выхода;
- выдачи багажа;
- впервые появившегося бортового номера.

Временный `null` не стирает ранее известное значение. Несколько изменений одного ответа объединяются в одно Telegram-сообщение.

## 7. Надежная доставка

Нормализованное состояние и notification event сохраняются одной SQLite-транзакцией. Доставки создаются по уникальным chat ID активных подписок. Worker повторяет Telegram 429 и временные ошибки с backoff. Успешная доставка не отправляется повторно после рестарта.

## 8. Ошибки провайдера

- HTTP 401 открывает глобальный `aeroapi_circuit` и приостанавливает polling;
- новый API key автоматически закрывает circuit breaker по изменению fingerprint;
- HTTP 403 считается ограничением тарифа или доступа конкретного endpoint и не блокирует другие endpoints;
- HTTP 429 и 5xx считаются временными и учитывают `Retry-After`;
- timeout и network error используют backoff;
- не-JSON ответ сохраняет HTTP-классификацию ошибки;
- 404 или временно пустой список не переключает подписку на другой маршрут.

## 9. Квота

Локальный лимитер считает исходящие HTTP-запросы. Он нужен для защиты от неконтролируемого polling, но не отражает тарифную стоимость разных endpoints FlightAware.

```text
AEROAPI_MONTHLY_REQUEST_LIMIT=10000
AEROAPI_REQUEST_RESERVE=500
AEROAPI_HARD_REQUEST_CAP=10000
AEROAPI_ALLOW_OVERAGE=false
AEROAPI_BILLING_CYCLE_DAY=1
```

Reserve доступен только высокоприоритетным активным рейсам. При hard cap новые запросы запрещаются, если overage отключен.

## 10. Конфигурация

Обязательные значения:

```text
TELEGRAM_BOT_TOKEN=
FLIGHTAWARE_AEROAPI_KEY=
```

Основные настройки:

```text
FLIGHTAWARE_AEROAPI_BASE_URL=https://aeroapi.flightaware.com/aeroapi
AEROAPI_MONTHLY_REQUEST_LIMIT=10000
AEROAPI_REQUEST_RESERVE=500
AEROAPI_HARD_REQUEST_CAP=10000
AEROAPI_ALLOW_OVERAGE=false
AEROAPI_BILLING_CYCLE_DAY=1
AEROAPI_MAX_CONCURRENCY=5
AEROAPI_EXTENDED_LOGGING=false

BOT_DEFAULT_TIMEZONE=Europe/Moscow
DATABASE_PATH=/data/flights.db
SCHEDULER_TICK_SECONDS=30
SCHEDULER_BATCH_SIZE=20
FLIGHT_LEASE_SECONDS=120
HTTP_CONNECT_TIMEOUT_SECONDS=10
HTTP_READ_TIMEOUT_SECONDS=20
```

Все числовые значения проверяются при старте. Telegram token и AeroAPI key не должны находиться в репозитории, image или логах.

## 11. Docker и жизненный цикл

Штатный запуск:

```text
docker compose build
docker compose up -d
docker compose logs -f flight-bot
```

Требования:

- один экземпляр приложения;
- `restart: unless-stopped`;
- непривилегированный пользователь;
- persistent volume `/data`;
- healthcheck по SQLite и heartbeat локальных workers;
- graceful shutdown с закрытием Telegram и HTTP sessions;
- внешний API не должен вызывать Docker restart loop.

## 12. Обязательные тесты

Минимальный набор:

- валидация `/flight` и прямой даты;
- callback data не превышает 64 байта;
- недоступные дни календаря неактивны;
- auth header и точные query params AeroAPI;
- ключ отсутствует в логах;
- non-JSON 403 сохраняет HTTP-код;
- numeric airline designator;
- нормализация live flight и schedule;
- перевод UTC в timezone аэропорта;
- фильтрация расписания по локальной дате;
- выбор не зависит от порядка ответа;
- `fa_flight_id` имеет приоритет при повторном сопоставлении;
- другой маршрут не подменяет отслеживаемый рейс;
- diff, пороги и сохранение transient values;
- квота и protected reserve;
- последняя отписка останавливает polling;
- один event создает одну доставку на чат;
- suspended future flight восстанавливает `future_scheduled`.

Проверки:

```text
pytest
ruff check .
ruff format --check .
```

## 13. Критерии приемки

1. Обычный текст с номером не вызывает AeroAPI.
2. `/flight FV6106` открывает выбор даты.
3. `/flight FV6106 YYYY-MM-DD` запускает тот же поиск без календаря.
4. Команда в группе создает доставку в эту группу.
5. Бот использует заголовок `x-apikey` и актуальный base URL AeroAPI.
6. Live-поиск использует `/flights/{ident}`.
7. Дальний поиск использует `/schedules/{date_start}/{date_end}`.
8. Локальная дата вычисляется по timezone аэропорта отправления.
9. После первого ответа сохраняется и используется `fa_flight_id`.
10. Бот не выбирает первый элемент ответа вслепую и не переключает маршрут.
11. Один физический рейс опрашивается один раз для всех подписчиков.
12. Состояние и outbox переживают перезапуск.
13. API key и Telegram token отсутствуют в логах.
14. Hard cap не допускает запросы сверх лимита при отключенном overage.
15. README, `.env.example`, код и тесты описывают FlightAware AeroAPI без ссылок на старый провайдер.
